# Wingman.OS Core — Mangasm+ Live Mix Voting Engine

FastAPI service that lets Mangasm+ members vote for the Friday / Saturday live SoundCloud
mixes. Votes are recorded atomically in Supabase (Postgres) via the `cast_mix_vote` RPC,
duplicates are rejected, and every response carries the fresh queue rankings.

This directory is self-contained and independent of the Java build in the rest of the
repository: it has its own dependencies (`requirements.txt`), tests (`pytest`) and container
image (`Dockerfile`).

## Endpoints

| Method | Path                        | Purpose                                     |
|--------|-----------------------------|---------------------------------------------|
| POST   | `/api/v1/swarm/audio/vote`  | Cast a vote for a live mix                  |
| GET    | `/api/v1/health`            | Liveness probe (never calls Supabase)       |
| GET    | `/docs`                     | OpenAPI UI (generated by FastAPI)           |

### `POST /api/v1/swarm/audio/vote`

Request:

```json
{ "user_id": "user-123", "mix_id": "golden-hour-progressive-house" }
```

Identifiers are 1–128 characters from `[A-Za-z0-9_.:@-]`. Unknown fields are rejected.

Success (`200 OK`):

```json
{
  "user_id": "user-123",
  "mix_id": "golden-hour-progressive-house",
  "vote_count": 42,
  "vote_timestamp": "2026-09-11T20:15:03.412819+00:00",
  "rankings": [
    { "rank": 1, "mix_id": "golden-hour-progressive-house", "title": "Golden Hour Progressive House | 4K DJ Set",
      "artist": "MATRYXX & BERKO", "session_slot": "friday", "vote_count": 42 },
    { "rank": 2, "mix_id": "midnight-melodic-techno", "title": "Midnight Melodic Techno",
      "artist": "Resident", "session_slot": "friday", "vote_count": 40 }
  ]
}
```

Rankings cover the open mixes in the same session slot (`friday` / `saturday`) as the mix
voted for, ordered by `vote_count desc, created_at asc`, capped at `RANKINGS_LIMIT`.

Errors share one shape, `{"error": {"code": "...", "message": "...", "details": {...}}}`:

| Status | `code`                 | When                                                        |
|--------|------------------------|-------------------------------------------------------------|
| 400    | `INVALID_INPUT`        | Missing / malformed `user_id` or `mix_id`, bad JSON          |
| 403    | `MEMBERSHIP_REQUIRED`  | No subscription record or not an active Mangasm+ member (message: `M+ Membership Required`) |
| 404    | `MIX_NOT_FOUND`        | Unknown mix, or voting is closed for it                      |
| 409    | `DUPLICATE_VOTE`       | The member already voted for this mix                        |
| 500    | `UPSTREAM_UNAVAILABLE` | Supabase failed on all retry attempts (default 3)            |

## Request flow

1. **Validate input** — pydantic model; validation failures map to `400`.
2. **Membership check** — `GET /rest/v1/mangasm_subscriptions?user_id=eq.<id>`. The member
   is Mangasm+ when `tier` is a plus tier, `status` is `active`/`trialing`, and
   `current_period_end` is null or in the future. Anything else → `403`.
3. **Atomic vote** — `POST /rest/v1/rpc/cast_mix_vote`. Inside one transaction the function
   locks the mix row, inserts the `(user_id, mix_id)` vote record (primary key ⇒ duplicates are
   impossible even under concurrent requests), increments `live_mixes.vote_count` and returns
   the new count plus the rankings. It raises `PT409 DUPLICATE_VOTE` / `PT404 MIX_NOT_FOUND`,
   which PostgREST surfaces as HTTP 409 / 404 and the service maps to the codes above.
4. **Respond** with the count and rankings.

Every Supabase call is retried up to `SUPABASE_MAX_ATTEMPTS` (default 3) on network errors,
timeouts and HTTP 408/425/429/5xx with exponential backoff (`SUPABASE_RETRY_BACKOFF_SECONDS`,
doubling). 4xx responses are never retried. When retries are exhausted the API returns `500`.

### Logging

Logs are JSON lines on stdout. Each vote attempt emits one audit line with `user_id`,
`mix_id`, `vote_timestamp` and `outcome` (`accepted`, `membership_required`, `duplicate`,
`mix_not_found`, `upstream_unavailable`, `upstream_error`). Retries are logged at `WARNING`.

## Configuration

| Variable                          | Required | Default | Notes                                                |
|-----------------------------------|----------|---------|------------------------------------------------------|
| `SUPABASE_URL`                    | yes      | —       | e.g. `https://xyz.supabase.co`                       |
| `SUPABASE_KEY`                    | yes      | —       | **Service role** key. Server-side secret only.       |
| `SUPABASE_TIMEOUT_SECONDS`        | no       | `5`     | Per-request timeout                                  |
| `SUPABASE_MAX_ATTEMPTS`           | no       | `3`     | Attempts per Supabase call                           |
| `SUPABASE_RETRY_BACKOFF_SECONDS`  | no       | `0.2`   | Base backoff; doubles per attempt                    |
| `RANKINGS_LIMIT`                  | no       | `20`    | Queue entries returned per vote (1–100)              |
| `LOG_LEVEL`                       | no       | `INFO`  |                                                      |

The process refuses to start if `SUPABASE_URL` or `SUPABASE_KEY` is missing. A local `.env`
file is honoured (see `.env.example`).

## Database

Apply `supabase/migrations/0001_live_mix_voting.sql` (Supabase CLI: `supabase db push`, or the
SQL editor). It creates:

- `mangasm_subscriptions (user_id, tier, status, current_period_end)` — membership source of truth
- `live_mixes (mix_id, title, artist, session_slot, source_url, description, voting_open, vote_count, …)`
- `mix_votes (user_id, mix_id, voted_at)` with primary key `(user_id, mix_id)`
- `cast_mix_vote(p_user_id, p_mix_id, p_voted_at, p_rankings_limit) returns jsonb` — `security definer`,
  executable by `service_role` only

Row level security is enabled with no policies, so only the service role can read or write
these tables. `supabase/seed.sql` seeds a demo Friday mix (Golden Hour Progressive House by
MATRYXX & BERKO) and three demo members for local testing.

## Run locally

```bash
cd wingman-os
python3 -m venv .venv && . .venv/bin/activate
pip install -r requirements-dev.txt
cp .env.example .env   # fill in SUPABASE_URL / SUPABASE_KEY
uvicorn app.main:app --port 8080 --reload

curl -s localhost:8080/api/v1/health
curl -s -X POST localhost:8080/api/v1/swarm/audio/vote \
     -H 'Content-Type: application/json' \
     -d '{"user_id":"plus-member-demo","mix_id":"golden-hour-progressive-house"}'
```

## Tests

```bash
cd wingman-os
pytest
```

The suite runs fully offline against an in-memory PostgREST stand-in (`tests/conftest.py`)
and covers the acceptance criteria: plus members vote and the count updates atomically,
non-plus members get `403`, duplicate votes get `409`, plus input validation, retry/500
behaviour and audit logging.

## Deploy (Wingman.OS Core)

```bash
docker build -t wingman-os/live-mix-voting wingman-os
docker run -p 8080:8080 -e SUPABASE_URL=... -e SUPABASE_KEY=... wingman-os/live-mix-voting
```

- Health check: `GET /api/v1/health` (also wired as the container `HEALTHCHECK`).
- Secrets: `SUPABASE_KEY` must come from the platform secret store, never an image layer or
  client bundle.
- Trust boundary: the endpoint trusts `user_id` as supplied. Run it behind the Wingman.OS
  gateway that authenticates members and injects/validates `user_id`; do not expose it
  directly to browsers.
- Retries are not idempotent by design: if a vote commits but the response is lost and the
  gateway retries, the second attempt returns `409`, which clients should treat as success.
